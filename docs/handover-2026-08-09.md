### Stage 6's deliverable — the number that governs every recall reading

```
pooled_gate_recall_seed_sd = 0.0292        (3 pooled draws over 2,399 TESS rows)
```

> **A recall @1% FPR margin under ~0.034 is not a decision** — the analogue of
> AUC's ~0.009, derived by the same rule (`2 × seed_sd / √n_models`).

For a **difference between two runs** the bars combine in quadrature and are
recomputed per comparison: `2 × √((sd_a/√3)² + (sd_b/√3)²)`.

Recording both a fold-level and a pooled estimate was load-bearing: the
fold-level figure came out **2.4× larger** (0.0689), because a fold's TESS slice
holds ~215 negatives and its 1% FPR cut is two rows.

### Stage 7's sweep — all null, and one instructive false positive

Against `models/cv/branches-20260808-rebaseline` (TESS, n=2,399):

| arm | AUC | ΔAUC | R@1% | ΔR | verdict |
|---|---:|---:|---:|---:|---|
| control | 0.9202 | | 0.2196 | | |
| `unfolded` | 0.9135 | −0.0067 | 0.2204 | +0.0008 | null |
| `periodogram-clean` | 0.9213 | +0.0011 | 0.2536 | +0.0340 | *PASS by 0.00008* |
| `scalar_only` | 0.9094 | −0.0108 | 0.2792 | +0.0596 | null |

**Read all four as null.** `scalar_only` has the largest recall delta and reads
null; `periodogram-clean` has a smaller one and reads PASS — only because its
three draws happened to land within 0.005, giving an sd of 0.0029 against
`scalar_only`'s 0.0597. The classification is being made by noise in the error
bar, not by effect size. Full detail in `roadmap.md`.

`unfolded` being null means **not uniquely necessary**, not "carries no signal" —
leave-one-out cannot separate redundancy, and a joint drop would.

**Open hypothesis, not a result:** every drop raised shortlist recall while
holding or lowering AUC (+0.0008, +0.0340, +0.0596). Three independent arms
agreeing in sign, same shape as the capacity arm's real 0.145 → 0.236. Needs a
confirmatory design; three nulls pointing one way establish nothing.

## The three open decisions

1. **The offline control-arm harness — decided, not built.** Stage 7's real
   criterion (control-arm host-pass rate, 26.4% must fall) **cannot be measured
   for any branch model**: `ScoringEnsemble.from_registry` loads
   `cnn_dualview.keras`, and `TargetScorer` builds views with
   `preprocess.views.build_views`, not `preprocess.viewset`'s eleven. Adding a
   run-directory flag to `injection_recovery.py` is necessary and nowhere near
   sufficient.

   Agreed approach: an **offline** harness — `clean`/`flatten` →
   `inject_box_transit` → `build_view_set(lc, *, period, t0, duration)` →
   `write_viewset_shards` → `make_viewset_dataset` → the run directory's members
   and calibrator. One script, one test file; compute is forward passes over
   cached FITS. **Not started.**

   Two limits are pre-registered in `roadmap.md` and must survive into the
   result: the offline control arm runs `detection`/`ghost` masked (no DV report
   at a synthetic ephemeris), and it does **not** restore comparability with
   26.4% — the incumbent must be re-measured on the same protocol, and the
   number can never support a *serving* claim.

2. **`select_hosts` has no baseline matching.** The harness owed since old 2(b)
   does not exist. Its selection source differs by path — `labels.parquet` + the
   FITS cache for the live path, the viewset index for the offline one — which is
   why it was not built speculatively. Note `labels.parquet` has no
   `expected_transit_count`, so `baseline_days` needs a join against the viewset
   scalars.

3. **Whether to widen the sweep.** Five families are unmeasured (`flux`,
   `global`, `trend`, `centroid`, `gap`). Given every measured arm came back
   null, the value of more leave-one-out runs is questionable — a **joint** drop
   would test redundancy, which is what the nulls actually point at.

## Operational facts that live nowhere else

- **Run the test suite one process per file.** Repeated `run_cv` calls in a
  single process get monotonically slower — 86s, 108s, 161s, 190s for four
  *identical* runs, and a file with eighteen of them did not finish in three
  hours. `clear_session()` does **not** help; the cause is open (candidates:
  `tf.data` iterator/`.cache()` retention, Metal allocator fragmentation).

  ```bash
  for f in pipeline/tests/test_*.py; do python -m pytest "$f" -q -p no:randomly; done
  ```

  Whole suite ~5.5 min this way. **534 pipeline + 32 api green** at `76c8ff4`.
  Any new test calling `run_cv` should consume an existing module-scoped fixture.

- **A CV run is ~70 min**, not the handover-2026-08-08 estimate of 60 or the ~2h
  a loaded machine suggested. Clean measurement: `unfolded`, 5 folds at
  `--n-models-per-fold 3`, **67m40s** (12:22, 15:52, 18:03, 10:45, 10:38 per
  fold — no within-run degradation, so the accumulation above does not bite a
  single run).

- **Never pipe a long run through `tail`.** It buffers, so a three-hour run gives
  zero progress output. Redirect to a log and tail the log.

- **Hibernation does not perturb training.** The machine hibernated mid-sweep at
  1% battery; the two `periodogram` runs (one spanning it, one clean) agree
  within noise on both statistics — recall differs 0.0158 against a 0.0383 bar.
  Processes survive and resume; check `elapsed` vs CPU `time` to detect it.

- **`git add docs/` is a trap.** It swept another session's untracked file into a
  commit. Stage explicit paths.

- The working tree carries two things this session did not author and left
  alone: untracked `docs/demo-script-2026-08-08.md`, and an `animejs` addition in
  `frontend/package.json`. Both make `run_config.git_dirty` read `True`; no
  tracked *pipeline* file differs.
